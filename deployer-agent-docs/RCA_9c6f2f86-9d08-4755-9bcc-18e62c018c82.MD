# RCA — spiloveure.com : boucle de redirection vers /dashboard + soldes à 0 (PROD uniquement)

## Verdict
**Cause racine = incompatibilité entre le mode d'export web Expo (`web.output: "static"`) et le service SPA du template de déploiement `farm` (Cloudflare + fallback `index.html`).**
Aucune des hypothèses backend/secrets/DB n'est en cause.

- **H1 (bundle stale)** : PARTIELLEMENT lié mais PAS la cause — le build frontend du dernier run (`9c6f2f86`) a bien tourné et poussé les assets courants vers R2 (`Step #8 frontend-build-push ... build completed successfully`). Les assets servis sont à jour, mais dans le **mauvais format**.
- **H2 (mauvais REACT_APP_BACKEND_URL / backend injoignable)** : ❌ RÉFUTÉE. Les logs backend prod montrent le frontend Cloudflare (IP 34.111.46.36) qui atteint `/api/*` avec **200 OK** en continu.
- **H3 (service worker)** : ❌ non causal. Il existe bien un SW `public/firebase-messaging-sw.js`, mais c'est du Firebase Cloud Messaging, il n'intercepte pas la navigation. La reproduction en navigation privée exclut d'ailleurs le cache/SW.
- **H4 (backend down / Mongo non bindée)** : ❌ RÉFUTÉE. Endpoints protégés (`/api/dashboard`, `/api/missions`, `/api/me/*`) tous en 200. DB `spiloveure-deploy-spilivere` bindée, 51 collections, 11 847 users.
- **H5 (JWT_SECRET différent)** : ❌ RÉFUTÉE. Si le JWT ne validait pas, les endpoints protégés renverraient 401 — ils renvoient 200.
- **H6 (edge re-route toutes les routes vers /dashboard)** : ✅ **VRAIE cause, mais l'origine n'est pas une "mauvaise règle edge" — c'est le comportement NORMAL du fallback SPA farm face à un export multi-HTML Expo.**
- **H7 (backend renvoie balance 0)** : ❌ RÉFUTÉE. La DB contient de vrais soldes non nuls, ex. user `admin` : `balance_profit: 95270`, `commission_direct: 54000`, `commission_spillover: 52500`, `total_earned: 106500`. Le "0 XOF" est un défaut de **rendu frontend**.

## Preuves
1. **Build logs run 9c6f2f86** : le frontend est une app **Expo / expo-router** exportée en **web statique** — `node_modules/expo-router/entry.js`, `Using build directory: dist`, et des fichiers HTML **par route** poussés vers R2 : `tasks-more.html`, `transactions.html`, `(admin)/ashtec-diag.html`, etc.
2. **`frontend/app.json`** :
   ```json
   "web": { "bundler": "metro", "output": "static", ... }
   "plugins": ["expo-router", ...]
   ```
   `output: "static"` ⇒ `expo export --platform web` génère **un HTML par route** (SSG), avec des URLs propres sans `.html`.
3. **`frontend/app/index.tsx`** (route racine `/`) :
   ```js
   if (user) {
     if (user.role === "admin") router.replace("/(admin)");
     else router.replace("/(app)/dashboard");
   }
   ```
   ⇒ la racine renvoie SYSTÉMATIQUEMENT tout utilisateur connecté vers `/dashboard` (ou `/(admin)`).
4. **`frontend/public/`** : aucun fichier de rewrite (`_redirects`, `_routes.json`) qui mapperait `/marketplace` → `marketplace.html`.
5. **`frontend/package.json`** : le mode preview est `expo start --web` (serveur dev Metro = SPA client en mémoire), fondamentalement différent de l'export statique servi en prod.
6. **Template de déploiement** = `fastapi_react_mongo_shadcn_base_image` (farm), `frontend_type: cloudflare`. Le service frontend farm applique un fallback type SPA `try_files $uri /index.html` : toute route non résolue en asset statique est servie par la racine `index.html`.
7. **Backend/pods** : run actif `9c6f2f86` sain (2 pods Running, ready). Quelques sondes liveness/readiness 503 intermittentes (le backend ne monte pas de route `/health`, seulement `/api/...`) mais sans crash ni restart — non lié au bug utilisateur.

## Mécanisme exact du bug (pourquoi PROD casse, PREVIEW non)
- **Preview** = `expo start --web` : routing 100% client en mémoire, aucune requête document vers un hôte statique ⇒ tout fonctionne.
- **Prod** = export statique multi-HTML servi derrière le fallback SPA farm. Dès qu'une navigation déclenche une vraie requête document vers une URL propre (`/marketplace`, `/tasks`, refresh, deep-link, ou navigation document de l'export statique), l'hôte ne trouve pas d'asset `/marketplace` (le fichier réel est `marketplace.html`) ⇒ **fallback vers la racine `index.html`** ⇒ `app/index.tsx` s'exécute ⇒ `router.replace("/(app)/dashboard")`.
- Résultat visible : l'onglet cible s'affiche brièvement (rendu client instantané) puis **retombe sur /dashboard** (re-boot à la racine). Idem sur tous les onglets, tous les comptes, même en navigation privée.
- **Soldes à 0** : à chaque re-boot forcé à la racine, le Dashboard se remonte à froid avec ses valeurs par défaut (0) ; les données réelles (bien présentes côté API/DB) ne se stabilisent pas à l'écran. Le **scroll qui remonte tout seul** = conséquence directe des rechargements document (reset du scroll).

## Correctif recommandé (fix CODE, à appliquer par E1 puis redéployer)
**Passer l'export web en mode SPA single-page**, compatible avec le fallback `index.html` du template farm.

Dans `frontend/app.json` :
```json
"web": {
  "bundler": "metro",
  "output": "single",     // <-- remplacer "static" par "single"
  ...
}
```
Effet : `expo export --platform web` produit **un seul `index.html`** + le bundle JS ; tout le routing devient client-side (exactement comme le preview). Chaque deep-link/refresh sert le même `index.html`, expo-router restaure la bonne route côté client ⇒ plus de retombée racine → dashboard, et le Dashboard rend ses soldes normalement.

Étapes :
1. Éditer `frontend/app.json` : `"output": "static"` → `"output": "single"`.
2. Redéployer (le frontend est reconstruit, le bundle single-page est poussé vers R2, le pointeur de version est mis à jour au promote).
3. Valider sur spiloveure.com : login → cliquer chaque onglet (Tâches, Marketplace, Publicités, Ads) → la route doit tenir sans retomber sur /dashboard ; les soldes doivent afficher les vraies valeurs (ex. compte admin ≈ 95 270 de profit).

### Alternative (déconseillée)
Garder `output: "static"` et ajouter des règles de rewrite hôte (extensionless → `.html`). Non recommandé : le worker Cloudflare du template farm n'est pas éditable depuis la source de l'app et n'honore pas de façon fiable un `_redirects` pour ce cas — le mode `single` est la correction propre et alignée avec le comportement déjà validé en preview.

## Limites de cette investigation (transparence)
- La boucle de redirection navigateur n'a **pas été reproduite dans un navigateur** (le sandbox n'a pas de navigateur). Le diagnostic s'appuie sur : `app.json` (output static), les build logs (HTML multi-route en `dist`/R2), `app/index.tsx` (redirect racine → dashboard), l'absence de rewrites, le mode preview `expo start`, et l'état sain confirmé du backend + DB. L'ensemble est cohérent et concluant.
- `firebase-messaging-sw.js` reste présent : sans lien avec le bug, mais si des soucis de cache persistent après le fix, une purge SW peut être conseillée à l'utilisateur.

## Nettoyage éventuel (non bloquant)
- Le backend n'expose pas de route `/health` (d'où les sondes liveness/readiness 503 intermittentes vues côté K8s, sans impact car pas de crash). À traiter séparément si besoin, indépendant du bug utilisateur.
